На всех этапах:

- только основной runtime в `game/`; превью в `art_working/` не подключать как production;
- использовать blockout, native Godot UI и placeholders;
- не копировать draft PNG, сцены и ресурсы из `art_working/` в `assets/`;
- не объявлять изображения `approved` без отдельного визуального review пользователя;
- не добавлять addons, test frameworks, localization frameworks, серверный слой или другие зависимости без отдельной измеримой необходимости и согласования;
- не реализовывать multiplayer, кланы, PvP, торговую площадку, сложную процедурную генерацию, новые главы, полноценный магазин и production-арт;

- не делать `commit`, `push`, `reset`, `rebase` и другие git-мутации без отдельной просьбы;
- сохранять portrait 180×320, nearest, integer scaling и существующие input actions `primary`, `secondary`, `inventory`, `checkpoint`;
- keyboard использовать для desktop smoke test, но не вместо touch/mouse-ввода;
- не связывать UI напрямую с RNG, `FileAccess`, сохранением или генерацией добычи;
- не сериализовать живые Node/Resource/Object и не привязывать save DTO к NodePath;
- не переносить из чернового монтажа циклический возврат на сам монтаж как production-маршрут;
- не расширять этап незапрошенными системами. Если найден unrelated bug, зафиксируй его отдельно, а не исправляй без необходимости.

## 6. Обязательная последовательность этапов

Тесты начинаются вместе с первыми доменными правилами. Отдельный этап headless suite после первого боя означает расширение и стабилизацию проверок, а не отказ от тестов до этого момента.

### Этап 0. Ревизия, архитектура и план

**Цель:** получить подтверждаемую основу, не меняя игровой код.

Выполни описанные выше ревизию и архитектурный контракт. Построй dependency graph и таблицу этапов с входами, выходами и acceptance gates. Укажи, какие решения нужно утвердить до кода. Если активен plan mode или пользователь просил сначала план, остановись до разрешения изменений.

**Гейт:** есть однозначные владельцы состояния, минимальные контракты, отсутствуют дублирующие системы, известны команды проверки и открытые вопросы.

### Этап 1. Состояние игрока и данные героя/врагов

**Цель:** создать тестируемое доменное ядро без UI, сохранения и RNG.

Минимум:

- HP: current/max, clamp, урон, лечение, смерть;
- основной stat и необходимые производственные статы;
- уровень, опыт и правило повышения;
- один минимальный выбор улучшения только в объёме, необходимом критерию MVP;
- определения героя, моховой слизи и гоблина-лазутчика;
- подготовка definition-контракта предметов для следующих этапов;
- отделение authoring `Resource`/`.tres` от runtime state;
- отсутствие изменений shared Resource templates при создании/изменении экземпляров.

Не выбирай сложную RPG-формулу на будущее. Зафиксируй одну понятную damage formula и округление один раз в конце. Числа вынеси в данные и пометь баланс как blockout-гипотезу.

**Автоматические проверки:**

- каждый `.tres` загружается как ожидаемый класс;
- обязательные ID уникальны и не пусты;
- runtime-копии независимы от definitions;
- HP никогда не выходит за допустимые границы;
- смерть наступает ровно при заданном условии;
- повторные сигналы смерти не создают повторных эффектов;
- level-up работает на границе XP и не теряет остаток XP, если это предусмотрено контрактом;
- два одинаковых definition могут иметь независимое runtime HP.

**Гейт:** доменные правила работают без инстанцирования боевой сцены и UI; тесты имеют корректный ненулевой exit code при ошибке.

### Этап 2. Первый playable blockout-бой: слизь и гоблин

**Цель:** один повторяемый боевой runtime и два последовательных encounter на общих правилах.

Слизь идёт первой по narrative Scene 04, гоблин — следующим противником по Scene 05. Не делай одновременную crowd-битву. Повторно используй боевую сцену и различай противников данными/поведением, а не копированием всего кода.

Минимальные возможности:

- атака героя;
- уклонение или защита через существующий action;
- понятный телеграф противника;
- явные startup/active/recovery или эквивалентные состояния;
- vulnerability window;
- урон не чаще одного раза за одну атаку;
- HP обеих сторон;
- однозначные победа и поражение;
- запрет боевых действий после терминального состояния;
- полный retry без старого HP, timers, tween callbacks и flags;
- touch/mouse и desktop keyboard smoke;
- placeholder UI для HP, телеграфа, доступных действий, победы/поражения и retry.

Поведение:

- слизь: сжатие → прыжок → открытое ядро после прыжка;
- гоблин: читаемый замах/двойной slash → отступление и окно ответа;
- конкретные окна и числа считать гипотезами до playtest.

Боевой resolver не должен зависеть от `Control`, `AnimatedSprite2D`, `AnimationPlayer`, wall clock, `FileAccess` или глобального RNG. Представление подписывается на состояние/события и не определяет попадание по кадру анимации. Для правил используй deterministic tick/advance contract.

**Проверки:**

- отдельные headless-тесты атаки, dodge success/failure, телеграфа, vulnerability, однократного урона, победы, поражения и retry;
- оба противника проходят одинаковый базовый lifecycle;
- повторный запуск действительно эквивалентен новому бою;
- playable smoke через реальный ввод;
- читаемость и отсутствие clipped/overlapping UI на 180×320, 360×640, 390×844.

**Гейт:** пользователь может понять, когда защищаться и когда атаковать; победа и поражение достижимы; правила проверяются без UI.

### Этап 3. Общий headless suite игровых правил

**Цель:** собрать надёжный regression runner для текущих и последующих систем.

Используй `SceneTree` runner без внешнего test framework. Он должен:

- явно считать passed/failed;
- считать незавершённый тест ошибкой;
- заканчиваться `quit(1 if failed > 0 else 0)`;
- избегать bare `assert()` как единственного критерия;
- ограничивать ожидания, чтобы failure не превращался в бесконечный hang;
- использовать deterministic ticks и seed;
- печатать понятные имена failed checks;
- корректно освобождать созданные объекты.

Минимальные команды из корня репозитория:

```bash
godot --headless --path game --import
godot --headless --path game --script res://tests/test_runner.gd
```

Если binary называется иначе или задан через `GODOT_PATH`/другой project setting, используй фактический настроенный путь и задокументируй команду. Не утверждай, что проверка запущена, если binary недоступен.

Проверь отдельно:

- отсутствие `SCRIPT ERROR` и неожиданных `ERROR` в логах;
- покрытие разрешённых и запрещённых переходов;
- границы окон телеграфа/attack/dodge;
- урон ровно один раз;
- HP clamp;
- победу и поражение;
- отсутствие мутаций после terminal state;
- retry обоих противников;
- отсутствие влияния UI и кадровой частоты на результат deterministic scenario.

Обязательно проверь сам runner: временно сломай одно ожидание, убедись в exit code 1, затем верни правильное ожидание и снова получи 0. Не оставляй намеренную поломку в deliverable.

**Гейт:** свежий import и полный suite проходят; runner доказанно способен падать; smoke-лог чист.

### Этап 4. Добыча, инвентарь и экипировка

**Цель:** завершить цикл «победа → награда → хранение → сравнение → экипировка».

Минимум:

- награда выдаётся только после победы;
- reward transaction идемпотентна: повторный сигнал не дублирует предметы;
- `LootGenerator` получает seed/RNG извне;
- определения предметов имеют стабильные IDs;
- runtime stack/instance имеет отдельный контракт и при необходимости instance ID;
- качество/редкость и аспект, где применимо к Кристаллам Эха;
- экран награды с сравнением;
- принять, отправить в инвентарь, надеть;
- список/сетка, фильтр по типу, equip/unequip;
- состояние сохраняется при переходах между сценами;
- placeholder UI, IDs и текстовые placeholders вместо финальных иконок.

Экипировка не должна перезаписывать base stats. Derived stats пересчитываются как base + modifiers; modifiers удаляются по `source_id`, а не по совпадающему числовому значению. Зафиксируй одно правило current HP при изменении max HP — сохранение абсолютного HP с clamp либо сохранение ratio — и применяй его везде. Equip/unequip не должен быть бесплатным лечением.

**Тесты:**

- одинаковый seed даёт одинаковый reward;
- награда начисляется один раз;
- add/remove/stack и запрет недопустимых операций;
- фильтр возвращает правильные типы;
- equip каждого предмета изменяет только заявленные статы;
- unequip удаляет modifiers именно этого источника;
- equip → unequip возвращает весь stat block точно к исходному;
- замена двух предметов с одинаковыми modifiers не удаляет чужой modifier;
- повторный equip не складывает modifier дважды;
- изменение max HP не создаёт бесплатное лечение;
- переход сцен не очищает inventory/equipment;
- UI награды и инвентаря работает на трёх portrait sizes.

**Гейт:** сквозной сценарий победы и экипировки работает без прямого доступа UI к RNG или сохранению; все round-trip тесты зелёные.

### Этап 5. Checkpoint и восстановление

**Цель:** реализовать narrative-правила как согласованные доменные транзакции, а не как кнопку retry.

Checkpoint — deep snapshot, независимый от последующих изменений текущего профиля. Нельзя хранить ссылку на живой mutable state вместо снимка.

Текущие правила:

1. Одновременно не более трёх ручных Checkpoint.
2. Создание только вне боя и преследования.
3. Фиксация занимает пять секунд, герой должен оставаться на месте.
4. Снимок включает тело/HP, уровень, обычный XP, экипировку, инвентарь, валюту, задания и состояние локального мира.
5. После смерти игрок выбирает точку; если не выбирает, применяется последняя созданная.
6. Выбранная точка исчезает после использования.
7. При возврате к более ранней точке более поздние также исчезают.
8. Новая четвёртая ручная точка требует явного удаления существующей; случайной перезаписи нет.
9. Первый след создаётся автоматически; если точек нет, он восстанавливается принудительно.
10. Цена fallback: потеря всех незакреплённых Кристаллов Эха и два Следа Пустоты.
11. Память, Отголоски, купленные узлы адаптации, открытые техники Эха Мастерства и журнал противников сохраняются.
12. Уровень и обычный XP возвращаются к снимку; повторный восстановленный противник не даёт бесконечный XP/Отголоски.
13. Обычные предметы, деньги, HP, NPC, задания и разрушенные объекты возвращаются к снимку согласованно.
14. Каждая обычная смерть добавляет один След Пустоты: −10% max HP, максимум три Следа/−30%.
15. На третьем Следе после ближайшего возвращения герой принудительно отправляется в Лиорен и не может ставить новые точки до отдыха.
16. Отдых в безопасной зоне снимает все Следы, но не возвращает потраченные ресурсы и не отменяет сюжетные последствия.
17. Обычный профиль не создаёт жизнь, не расходуется и не заменяет Checkpoint.

Согласуй нумерацию с каноничными 11 пунктами Bible: здесь вложенные условия вынесены отдельно для проверки, это не новые механики.

UI должен объяснять цену и последствия через договор/Печать Пути, а не представлять возврат бесплатным retry. Ранний технический retry боя не должен незаметно обходить правила Checkpoint после их интеграции.

**Тесты:**

- создание разрешено/запрещено в правильных состояниях;
- движение, бой или преследование прерывают пятисекундную фиксацию;
- повторный tick после завершения не создаёт вторую точку;
- лимит три и запрет скрытой перезаписи четвёртой;
- snapshot не меняется при дальнейших изменениях профиля;
- выбор по умолчанию — последняя точка;
- выбранная и более поздние точки удаляются, более ранние остаются;
- уровень/XP/HP/инвентарь/экипировка/валюта/NPC/задания откатываются согласованно;
- память/Отголоски/узлы/техники/журнал сохраняются;
- продажа предмета → смерть → возврат не оставляет одновременно деньги и предмет;
- повторная победа после возврата не дублирует XP и первичные Отголоски;
- обычная смерть добавляет ровно один След;
- fallback добавляет два Следа и удаляет только предусмотренные незакреплённые Кристаллы;
- проверены 1, 2 и 3 Следа, округление max HP и current HP clamp;
- третий След вызывает принудительный отдых и запрет создания;
- отдых снимает Следы, но не воскрешает ресурсы и не отменяет мир;
- UI выбора/активации/возврата понятен на трёх viewport sizes.

**Гейт:** невозможно продублировать предметы, деньги или опыт через возврат; snapshot/restore целостен; правила видимы игроку и покрыты headless smoke tests.

### Этап 6. Один локальный профиль и сохранение

**Цель:** восстановить фактическое текущее состояние между запусками, не обходя стоимость смерти.

Минимум:

- один локальный профиль в `user://`;
- читаемый versioned JSON DTO;
- только primitive values, arrays, dictionaries, IDs и flags;
- версия схемы с первой реализации;
- defensive parse и validation до применения состояния;
- отказ загружать save с более новой версией;
- последовательные pure migrations для старых версий;
- атомарная запись через `.tmp` и сохранение предыдущего валидного файла как `.bak`;
- проверка всех возвращаемых `Error`;
- fallback на `.bak` при повреждённом primary;
- понятное пользователю сообщение, если сохранение/загрузка не удалась;
- autosave только на безопасных границах, не посреди активного боя;
- сохранение Checkpoint-снимков и мета-прогрессии в том же согласованном DTO, но без смешивания их семантики с текущим профилем;
- `Continue` и `New game` на Title; New game не затирает существующий профиль без подтверждения.

Учитывай Godot JSON number normalization: числа могут загружаться как float. Приводи целочисленные поля явно и не сравнивай целые Dictionaries без учёта этого правила. Большие IDs храни как strings. Не используй `store_var`/`str_to_var` с разрешёнными objects.

**Тесты:**

- round-trip всего фактического состояния: герой, XP, inventory, equipment, narrative flags, локальный мир, Checkpoints, Следы и мета-прогрессия;
- save → load → save не меняет семантику;
- повреждённый primary восстанавливает предыдущий `.bak`;
- отсутствие файла обрабатывается как отсутствие профиля, а не crash;
- malformed JSON и неполные данные отклоняются без частичного apply;
- newer version отклоняется;
- старая fixture проходит миграцию;
- ошибки записи не уничтожают предыдущий валидный профиль;
- сохранение не создаёт и не расходует Checkpoint;
- тесты используют отдельные test paths и удаляют только свои файлы.

После автоматических проверок выполни реальный quit/relaunch: изменить экипировку и состояние мира, сохраниться, полностью закрыть игру, запустить, продолжить и сравнить состояние. Если полноценный ручной relaunch недоступен, прямо отметь это как непроверенное, не подменяй его одним unit test.

**Гейт:** прогресс восстанавливается после реального перезапуска; повреждение и ошибки версий обрабатываются безопасно; UI не вызывает `FileAccess`.

### Этап 7. Перенос структуры диалогов и переходов из чернового монтажа

**Цель:** перенести narrative structure и input flow, а не draft-арт и не временную архитектуру превью.

Сохрани:

- стабильные `DIA_*` и `TUT_*` IDs;
- порядок сцен и реплик по каноничному документу;
- линейные сюжетные диалоги без вариантов ответа;
- tap/continue;
- `look` через отмеченную область/swipe там, где это есть в превью;
- `hold` с отменой при раннем отпускании;
- пагинацию длинных реплик;
- `parts` для одной реплики с несколькими визуальными частями;
- title card и явные scene destinations;
- `enter`/transition cues как команды presentation layer;
- `Once`/seen-флаги и восстановление NPC по состоянию Checkpoint;
- блокировку продолжения во время незавершённого transition.

Реализуй небольшой data-driven linear runner, а не новый scripting language. Текст, presentation cues и game commands должны быть разделены. Line IDs должны позволять позднее вынести локализацию без переписывания runtime. Не добавляй ветвления только ради generic dialogue system.

Dialogue runner может выдавать разрешённые команды владельцу narrative/session state, но не должен сам вызывать RNG или SaveService. Проверь whitelist команд и destinations. Не переноси из превью маршрут `post_montage → montage`, который служил только повторным показом.

Сначала используй blockout-фоны и native UI. Не копируй текстуры превью в `assets/`.

**Автоматические проверки:**

- IDs уникальны;
- все ссылки на следующие cues/scenes существуют;
- все commands/destinations входят в whitelist;
- нет узлов без выхода и недостижимых обязательных сцен;
- порядок ID совпадает с каноном;
- длинный текст пагинируется без потери содержимого;
- повторный tap во время transition не пропускает реплики;
- tap не завершает `hold`;
- раннее отпускание сбрасывает `hold`;
- завершённый `hold` срабатывает один раз;
- `Once` не повторяется после перехода сцен и восстанавливается после save/load;
- Checkpoint корректно восстанавливает NPC/narrative state по правилам;
- полный prologue доходит до gameplay без тупика;
- ввод и layout проверены на 180×320, 360×640, 390×844.

**Гейт:** структура и ввод монтажа доступны в основном runtime, связаны с gameplay destinations и не требуют draft-изображений.

### Этап 8. Финальная интеграция и документация

Проверь единый сценарий на фактическом deliverable:

```text
Новый профиль
→ пролог и интерактивные переходы
→ World
→ первая слизь
→ поражение и корректный retry/возврат
→ победа
→ награда
→ инвентарь и экипировка
→ гоблин
→ создание Checkpoint
→ изменение состояния
→ смерть и выбор возврата
→ проверка цены и отката
→ сохранение
→ полный выход
→ Continue
→ сверка всего состояния
```

Повтори полный headless suite и scene smoke. Проверь отсутствие дублей наград, потери состояния при переходах, старых таймеров после retry, clipped UI и новых файлов после проверок.

Обнови только подтверждёнными фактами:

- `game/README.md`;
- `PROGRESS.md`;
- затронутые architecture/design/narrative docs;
- `AGENTS.md`, если изменилось что-либо из документируемых им решений;
- список открытых вопросов и гипотез.

Отдельно перечисли, что не проверено: реальный Android, touch на устройстве, 30/60 FPS, production-арт и визуальный approval. Не записывай это как выполненное.

## 7. Единый протокол проверок для каждого implementation-этапа

Включи в задания K2.8 применимые команды:

```bash
godot --headless --path game --import
godot --headless --path game --script res://tests/test_runner.gd
```

Для scene smoke используй ограниченный по кадрам запуск и проверку лога, например:

```bash
godot --headless --path game --quit-after 300
```

Сам по себе exit code 0 smoke-запуска недостаточен: проверь `SCRIPT ERROR` и неожиданные `ERROR`. Не оставляй логи в репозитории ради отчёта; сохраняй только запрошенные проверочные артефакты в подходящем рабочем каталоге.

Если добавлены/перемещены `.gd`, `.tres` или сцены, проверь broken paths, UIDs и `class_name` после свежего import. Используй checker из `godot-nodes-scenes`, если он доступен. Не полагайся на единственный `--check-only`, если скрипт зависит от autoload/global class cache.

Для каждого UI-этапа проверь не только размеры окна, но и:

- integer scale;
- центрирование/letterbox;
- safe area;
- отсутствие clipped text;
- touch targets;
- focus для desktop smoke;
- читаемость телеграфа и состояния без зависимости только от цвета.
