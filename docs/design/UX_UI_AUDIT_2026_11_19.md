# UX/UI: аудит и план исправлений

Дата: 19 ноября 2026. Проверена текущая рабочая копия `main`, включая незакоммиченные изменения арт-интеграции. Статус документа: предложение для реализации и визуальной проверки; численные размеры и длительности ниже — рабочие гипотезы.

Основная проблема — композиция и поведение экранов. Арт добавлен к прежнему blockout: почти все экраны остались вертикальными формами с одинаковыми стандартными кнопками. В прологе фон, текст, рамка и действия не образуют единого диалогового интерфейса. Замена цвета кнопок сама по себе это не исправит.

Готовый исполнительный промпт: [KIMI_UX_UI_REWORK_PROMPT.md](KIMI_UX_UI_REWORK_PROMPT.md). Этот аудит содержит план, а не уже реализованный редизайн.

## Что проверено

- Все восемь экранов: Title, Prologue, World, Combat, Reward, Inventory, Checkpoint и общий GameRoot; сцены, экранные скрипты, SceneRouter, DialogueRunner, narrative JSON, ArtMap и связанные дизайн-документы.
- Godot 4.7.2, Compatibility; запуск отдельного процесса с `--save-path=user://ux_ui_audit_20261119.json`. Основной пользовательский профиль не использовался.
- Пролог проведён до World вызовами существующих команд runner; look/hold были завершены программно. Это осмотр состояний, а не полноценная проверка всех жестов человеком.
- Начало игры и подтверждение нового профиля проверены экранными кнопками. Synthetic touch в центре обычной реплики не изменил ни `runner.index`, ни `runner.page_index`.
- Сохранены [12 кадров текущего runtime](../reviews/ux_ui_2026_11_19/README.md). Reward показан с явно созданной тестовой наградой; Inventory — в пустом состоянии. Заполненный инвентарь и все варианты Checkpoint требуют отдельного прогона при реализации.
- При окне 390×844 измерены viewport 180×320, scale ×2 и offset `(15, 102)`. Сохранённые PNG показывают область контента 360×640, без внешних полос окна. Около 30% площади такого окна остаётся вне игрового кадра: `1 − (360×640)/(390×844)`.
- Существующий runner: `passed=50 failed=0 unfinished=0`, exit code 0, без SCRIPT ERROR. В журнале осмотра runtime до остановки — 0 ошибок и предупреждений. Процесс остановлен инструментом, его exit code 1 не использован как результат теста.
- Физический Android, DPI, вырезы, системные жесты, FPS на телефоне и реальная удобность чтения пальцем не проверены.

Текущие пользовательские изменения игровых файлов сохранены. Временный скрипт осмотра удалён; постоянные игровые сцены и код этим аудитом не менялись.

## Целевая композиция

### Диалог и катсцена

```text
┌────────────────────────┐
│ [История]       [Меню]  │  компактные вспомогательные действия
│                        │
│     СЮЖЕТНЫЙ КАДР       │  событие, жест, дорога, силуэт
│                        │
│ [портрет говорящего]    │  не перекрывает важное действие
├────────────────────────┤
│ Имя / мысли            │
│ Реплика в 3–4 строки.   │  единая защищённая область текста
│                    ▾   │  продолжить в той же панели
└────────────────────────┘
```

Панель в обычном состоянии ориентировочно 82–100 logical px из 320; конкретную высоту выбрать после проверки длинных русских реплик. Портрет — отдельный foreground-слой над панелью; имя и текст внутри её layout. Для внутреннего монолога можно использовать компактный тег «Мысли Харуто», без обязательного портрета. Полноэкранная иллюстрация уже с персонажами не требует дополнительного дублирующего портрета.

У Мицуки есть утверждённый `mitsuki_threshold_portrait.png` и ссылка ArtMap.MITSUKI_PORTRAIT, но текущий Prologue её не использует. Портретов всех остальных говорящих в нужном формате наличие не подтверждено: применять текстовое имя/силуэт или существующую сценическую подачу; отсутствующий арт вынести в отдельный brief. Полноэкранный клип со своим фоном не использовать как прозрачный портрет.

Показ текста сразу целиком — допустимый первый результат. Typewriter добавлять только с корректным поведением: первый tap раскрывает текущую страницу, следующий продвигает её. Скорость, история разговора, auto и skip — отдельные возможности; не создавать пустые кнопки заранее. В обычном диалоге не нужен одновременно большой «Далее», инструкция про Space и счётчик страниц.

### Мир и бой

```text
МИР                       БОЙ
┌────────────────────┐    ┌────────────────────┐
│ Герой · HP     Меню│    │ Противник · HP     │
│ Локация / цель     │    │                    │
│                    │    │                    │
│   ЛОКАЦИЯ / ГЕРОЙ  │    │    БОЕВАЯ СЦЕНА    │
│                    │    │                    │
│ Следующая встреча  │    │ Харуто · HP        │
│ [Идти к встрече]   │    │ [Уклонение] [Атака]│
│ Путь  Сумка Печать │    │                    │
└────────────────────┘    └────────────────────┘
```

World остаётся экраном текущего маршрута, а не новой системой свободного перемещения. После победы следующая доступная встреча становится основным действием; повтор боя остаётся явно доступен. В Inventory/Checkpoint использовать тот же визуальный язык и навигационный контекст. В прологе, бою и модальных подтверждениях постоянную нижнюю навигацию скрывать.

Для боя ориентир: 50–60% высоты под сцену, с проверкой исходных размеров спрайтов и pivot. Это композиционная гипотеза, не разрешение произвольно растянуть/обрезать спрайты или изменить боевую перспективу. Уклонение и атака различаются формой/иконкой/подписью; предупреждение содержит не только цвет. Cooldown объясняет недоступность действия вместо молча серой кнопки.

## Порядок реализации

### Итерация 1 — основа, Title и Prologue (P0)

1. Зафиксировать скриншоты «до» и текущее состояние Git. Создать общую Theme с primary/secondary/danger, normal/pressed/disabled/focus, размерами текста и отступами. Не добавлять новый UI-фреймворк или dialogue addon.
2. Собрать `SafeArea` и общую обработку modal/Back, сохранив GameRoot/SceneRouter. Для простых overlay достаточно одного локального host; новый глобальный менеджер экранов не требуется.
3. Пересобрать Title: одно рабочее название, ясный главный CTA («Начать путь» либо «Продолжить»), вторичная «Новая игра» и закрытое подтверждение замены профиля. Настройки добавлять только с работающими параметрами.
4. Сделать переиспользуемый `DialoguePanel`: подложка, имя, текст, индикатор, единый ввод. Рамку масштабировать через NinePatch/StyleBoxTexture только после определения пригодных border margins; иначе использовать аккуратный StyleBoxFlat в текущей палитре.
5. Исправить обычный tap, look-hitbox, swipe и hold-capture. Пока удержание активно, палец не должен случайно продвинуть следующую реплику после завершения; отпускание раньше порога отменяет шаг.
6. Убрать production debug-текст; desktop bindings показывать по режиму ввода. Представление не должно раскрывать технические shot ID или сведения о временной блокировке.
7. Переоформить кадры по смысловым блокам: рутина → дорога/опасность → бросок → последствия/тишина → разговор с Мицуки → дары → выход в мир. Сохранить 44 ID, порядок, полный канонический текст и `parts` дара. Для каждого блока определить фон, актёров, foreground, фокус и переход в presentation-данных.
8. Заменить произвольную нарезку по 88 символов на страницы, учитывающие ширину, шрифт и высоту панели. Измерение остаётся в presentation-слое; runner получает страницы/политику через небольшой явный контракт. Сохранить слова, пунктуацию, порядок и смысловые `parts`; смена размера не должна терять или повторять текст.
9. Увязать завершение перехода с реальной визуальной длительностью. Сейчас типовой lock равен 12 тикам, а вспышка длится около 1,17 сек: следующий текст может оказаться под продолжающимся эффектом. Не блокировать чтение без причины и не делать длинную анимацию обязательной для каждого клика.
10. Исправить Continue незавершённого пролога. Минимальная политика: возврат к первой не завершённой cue; текущая незавершённая реплика/`parts` могут начинаться сначала. Сейчас установка seen в `_complete_current()` сама по себе не уведомляет GameRoot о необходимости автосохранения: добавить явную безопасную границу сохранения после завершения cue через существующего владельца сохранений. Не сохранять каждый animation tick. Точное возобновление внутри страницы — отдельное расширение, не требование менять DTO сейчас. Seen, команды и завершение должны исполняться ровно один раз.

Готовность: первый экран и весь пролог выглядят связно; текст в панели, событие видно, жесты работают; перезапуск не выкидывает игрока из незавершённой истории. Требуются реальные кадры из изменённого runtime.

### Итерация 2 — мир, бой и меню (P1)

1. World: компактные HP/уровень и цель, герой в свободной зоне, карточка следующей встречи, контекст повторного боя. Для закрытого гоблина объяснить «Сначала победите слизь». Силу/защиту/ману перенести в подробности героя, не удаляя доступ к ним.
2. Combat: увеличить визуальный вес арены, собрать HP в компактные блоки, заменить ticks на полезную обратную связь, показать cooldown и результат. Статические подписи обновлять по событиям; каждый кадр обновлять только непрерывный визуальный прогресс. Не менять тайминги CombatResolver ради анимации.
3. Inventory: сохранить существующий фильтр; сделать одинаковые карточки/ячейки со значком и количеством. Tap — подробности и сравнение, отдельная кнопка — equip/unequip; материалы тоже открываются. Для малого количества предметов качественный список предпочтительнее пустой сложной сетки.
4. Reward: читаемая редкость, сравнение «надето / получено» и итоговых характеристик. Выбранное действие явно говорит, какой экран откроется; claim идемпотентен и блокируется после первого принятия.
5. Checkpoint: карточки существующих точек; выбор → предпросмотр цены и отката → подтверждение возврата. Показать расход выбранной и более поздних точек, Следы и fallback-потери. Отмена modal после смерти остаётся на обязательном выборе возврата. Отдельно подтвердить удаление точки; список не пересоздавать на каждый тик progress.
6. Объединить локализованные названия редкостей/аспектов и подписи действий в presentation-данных. `common`, `moss`, `goblin`, внутренние checkpoint ID не использовать как основной пользовательский текст.

### Итерация 3 — удобство истории и адаптация (P2)

- История реплик текущей сессии и настройка отображения текста. Повторное чтение не выполняет команды и не изменяет seen-флаги.
- Auto и skip только при наличии полноценной реализации: пауза на обязательных взаимодействиях, подтверждение skip, summary, однократные команды и корректное сохранение финального состояния. Это расширение согласованной линейной подачи, а не новые сюжетные развилки.
- Проверка звука/переходов при наличии утверждённых аудио; отсутствие звука не маскировать выдуманным результатом.
- Сравнить текущее letterbox с отдельным экспериментом адаптивного UI. В первой итерации оставить 180×320 и integer scale. Позднее можно расширить фон/безопасные UI-зоны на высоких экранах либо использовать world SubViewport с отдельным UI canvas, но только после документирования причины и визуального сравнения. Просто увеличить viewport до 1080×1920 — не решение.

## Размеры и ограничения

- Одна сетка, nearest и integer scaling для пиксельной графики остаются базой. Предварительные отступы: внешний 12 logical px; внутренний 6–8; шаги 2/4/8/12.
- Предварительно body 10–11 logical px, имя 11–12, секционный заголовок 13–14. На 360×640 при ×2 это 20–28 физических px. Эти числа не тождественны Android sp/dp и не доказывают читаемость на телефоне.
- Зона касания: сохранять минимум проекта 24 logical px; дополнительно измерить минимум 48×48 dp на Android, расстояние между целями ориентировочно 8 dp. Учитывать scale, screen density и letterbox offset, не приравнивать 24 logical px к 48 dp на любом устройстве.
- Контраст обычного текста — ориентир 4,5:1 по его реальной подложке; проверить на самом светлом и самом сложном кадре. Белая надпись на изображении без своей защиты не считается проверенной.
- Touch safe area пересчитывать из экранных координат в viewport с учётом transform/offset. На desktop нужен корректный fallback; headless не доказывает safe area устройства.

## Матрица приёмки

| Область | Обязательная проверка |
|---|---|
| Геометрия | 180×320 logical; окна 360×640, 390×844, 360×800, 412×915; одинаковые состояния и скриншоты с указанием фактического viewport/scale/offset. |
| Диалоги | Длинные русские реплики, один символ, `parts`, внутренний монолог, светлый фон, смена говорящего. Полный текст сохраняется, имя/портрет не заходят в текстовый rect. |
| Ввод | Один физический touch = одно логическое действие при включённой mouse emulation; mouse/Space также работают; быстрые нажатия не проскакивают cue. Tap на вспомогательной кнопке не продвигает историю. |
| Look/hold | Slow swipe по нескольким событиям; tap по реальному hotspot; hold success, раннее отпускание, уход пальца/потеря фокуса и отпускание после успеха. |
| Непрерывность | New game → частичный пролог → настоящий quit/relaunch → Continue → первая непрочитанная cue; законченный пролог ведёт в World. |
| Экраны | New/Continue и modal; оба монстра, telegraph/vulnerability/победа/поражение; награда; пустой и заполненный inventory, equip/unequip и материал; Checkpoint без точек/3 точки/фиксация/отмена/возврат/fallback/3 Следа/отдых. |
| Защита действий | Modal блокирует фон и фокус; Back закрывает верхний разрешённый слой; отмена не расходует точку/награду; повторный click не повторяет операцию. |
| Регрессии | Текущие 50 доменных cases проходят; новые тесты проверяют реальные риски — ввод, страницы, маршрутизацию, однократные side effects, а не точные декоративные координаты. |
| Устройство | Физический portrait Android: плотность, 48 dp, вырезы, жестовая панель, читаемость, удержание, запуск/возврат. Отметить отдельно от desktop synthetic touch. |

Субъективный playtest: новому игроку без устного объяснения дать начать путь, прочесть сцену, выполнить look/hold, найти следующую встречу, надеть предмет и понять цену возврата. Зафиксировать места остановки/ошибочных тапов и повторить после исправления. Это будущая проверка, а не уже полученные метрики.

## Открытые вопросы

1. Финальное название: до решения на титуле использовать существующее основное рабочее имя.
2. Нужны ли дополнительные портреты Харуто/Юи: сначала проверить имеющийся утверждённый арт, затем отдельный brief по art pipeline.
3. Какой минимальный Android и физическое тестовое устройство станут базой DPI/FPS-приёмки.
4. Оставить ли letterbox как продуктовую политику после первого исправления композиции.
5. Включать ли auto/skip уже в эту задачу или после первого визуально принятого пролога. P0/P1 не должны ждать этого решения.
